# 0013. Project file v2: one project document plus node settings

- Status: Proposed. Reconciled with the config API as built in #63 (see "Status after #63"); implementation is #37
- Date: 2026-11-17
- Deciders: technical lead

## Context
Today the configuration is four layered files: `devices.json` (generated by the KEPServerEX
importer), `devices_map.yaml` (SubDeviceId/topic per device), `overrides.yaml` (hand fixes
that survive re-import) and `poller.yaml` (runtime settings) (D-012). Layering was designed
for "KEPServerEX remains the source, opencap re-imports". A config API that creates and
edits channels, devices and tags (KEPServerEX Configuration API parity) has no natural place
to write in that layout. Redundant pairs must share the project but not node settings.

## Decision (proposed)
- **`project.json`** (schema version 2): channels, devices, tags, publish settings, north
  agents, processing plug-ins. It is the single source of truth that the API edits, with a
  `revision` counter, atomic writes and `config/.revisions/` history.
- **`node.yaml`**: what differs per node (instance name, bind addresses, data paths, names of
  secret env vars, redundancy role). Replaces `poller.yaml` (which keeps loading as v1).
- **KEPServerEX import** produces a project v2 by applying `devices_map.yaml` and
  `overrides.yaml` at import time (same rules as today). **Re-import** is a three-way merge:
  base = the previous import (`config/.import-base.json`), theirs = the new export, ours =
  the current project; conflicts are reported, never silently overwritten.
- v1 layouts keep loading unchanged; `opencap config migrate` writes v2 from v1. The config
  API works on a `ProjectStore` abstraction so storage can change without changing the API.

## Consequences
One editable document; the layering logic moves from runtime to import time.

## Alternatives considered
API writes into `overrides.yaml` (overrides grow into a second project); a database
(heavier, not diffable).

## Revisit when
Many concurrent editors per project (05 "revisit").

## Status after #63 (2026-11-18)
The configuration API merged in #63, **on the v1 layout**. `src/opencap/config/store.py`
(`ConfigStore`) edits `devices.json`, `devices_map.yaml` and `overrides.yaml`. Each change is
validated with the models, a staged loader run and the driver plan. Revisions are content
hashes exposed as `ETag`, with `If-Match` → 412. Multi-file commits are atomic with rollback,
the audit log is written inside the lock, and a write does not reload until `POST /reload` or
`?apply=true` (D-039–D-044). D-012 was amended: `devices_map.yaml` is now rewritten through
ruamel.yaml with its comments kept.

What this means for v2 (#37):
- #37 first extracts a `ProjectStore` protocol from `ConfigStore` (load, revision, commit,
  rollback, history) and makes the API depend on the protocol, not the class. Then it adds the
  v2 store (`project.json` + `node.yaml`) as a second implementation, and `opencap config migrate`.
- The `/map…` and `/overrides…` routes and the `files`-keyed export stay as **v1 compatibility
  routes** for installations that keep the KEPServerEX-managed layering. On a v2 project they
  answer 409 with a pointer to `/channels…`.
- The API's KEPServerEX import keeps the CLI's stub-append rules (D-012) on v1. On v2 it produces
  a project revision through the same `ProjectStore`.
- This ADR becomes Accepted when #37 merges.

## Status after #37 part 1
#37 is split in two (comment on the issue). Part 1 ships the v2 layout: `ProjectV2` and `NodeConfig`
with exported schemas; the loader (v2 when `project.json` exists, the shared finalize steps); `opencap
config migrate [--dry-run]`, which refuses to write unless v2 loads `Device`-equal to v1; and `import-kep
--format v2`. Until part 2 (the `ProjectStore` protocol and the v2 store with revisions), the config API
answers 409 on a v2 project for every store-backed route. North agents stay in `node.yaml` (today's
`poller.yaml` fields) until ADR-0005's north plug-in model exists. D-087.
