# IoT Gateway JSON payload (`publish.format: iotgw_json`)

Status: v1 (#36). Python reference: `src/opencap/north/payload_iotgw.py`. Vectors:
`tests/conformance/payload/iotgw/*.json` (generated by `scripts/gen_conformance.py`, area
`payload/iotgw`). The Rust engine must reproduce them byte for byte.

## Source

The shape follows the "standard template" of the KEPServerEX **IoT Gateway** MQTT Client agent,
described in the public KEPServerEX / Kepware IoT Gateway manual (PTC), chapters "MQTT Client
Agent" and "Payload templates" (the standard template). The manual is the public reference; this
file records what opencap writes. No KEPServerEX installation, export or private data was used.
Where the manual's wording left room, the choices are listed under "Differences".

## Selecting the format

Per device, in `devices.yaml`:

```yaml
publish:
  format: iotgw_json        # default: subdevice_json
```

The field is `PublishCfg.format` (`"subdevice_json" | "iotgw_json"`); the committed JSON Schema
(`schema/devices.schema.json`) lists both values and the default. It only changes the body of the
**data** message. Topics (`<prefix>/<channel>/<device>/data` or `publish.topic`), `mode`
(`interval` / `on_change`), `interval_ms`, `heartbeat_ms`, `deadband`, retain=false, QoS, the
store-and-forward outbox (D-016) and the retained `status` topic are all unchanged.

## Message

```json
{"timestamp":1794824101500,"values":[
  {"id":"Plant A.PLC1.FLOW_1","v":12.5,"q":true,"t":1794824101250},
  {"id":"Plant A.PLC1.PUMP_RUN","v":true,"q":false,"t":1794824090000}]}
```

Compact UTF-8 (separators `,` and `:`, raw non-ASCII, `allow_nan=False`), same encoder as the
SubDevice payload. Key order is fixed.

| Field | Rule |
|---|---|
| `timestamp` | Publish time, integer milliseconds since the Unix epoch (UTC), floored. |
| `values` | One entry per **enabled** tag, in the device's tag order, whatever its quality. Disabled tags are absent. Snapshot entries that are not tags of the device are ignored. |
| `id` | `<channel>.<device>.<tag name>`, names exactly as configured (the tag name already holds its group path, dot-joined, e.g. `Plant A.PLC1.LTI002.Pv`). No escaping of dots or spaces. |
| `v` | The tag value cleaned as for the SubDevice payload: floats rounded to `payload.float_decimals` places, `-0.0` written as `0.0`, bools stay bools, ints stay ints (64-bit exact), arrays element by element. A tag with no value, a `null` value, a NaN or infinite float (or array containing one) is JSON `null`. |
| `q` | `true` only when the quality is `good` and `v` is not `null`. `bad_comm`, `bad_config`, `bad_decode`, `stale` and a missing tag are `false`. |
| `t` | The tag's `source_ts` as integer milliseconds since the epoch (floored). A tag that has no source timestamp (never read, missing) gets the message `timestamp`. A bad tag keeps the source timestamp of its last good read. |

A bad tag keeps its last value in `v` (the cache keeps it) with `q: false`; consumers that care
about quality must check `q`. `payload.bad_tags_field` and `payload.timezone` do not apply to this
format. `isSecure`, `FirmVersion`, `SubDeviceId` and `Env` do not exist in it.

### Publish rules

Unchanged from the SubDevice format (`north/publisher.py`): a device that has never had a good
read publishes nothing; `on_change` decides on the rounded values with the device `deadband`
against the last published snapshot, plus the heartbeat. A message always carries every enabled
tag (a full snapshot), never only the tags that changed.

## Differences from KEPServerEX that we cannot or do not reproduce

- **Per-tag change-only messages.** KEPServerEX's agent can publish only the tags that changed
  ("Publish only on data change" per tag) and batch several updates per message. opencap
  publishes the whole device snapshot, as for SubDevice JSON, so every message has every tag.
- **One message per device.** KEPServerEX publishes per agent over a list of tags chosen in the
  agent; opencap publishes per device, with the topic as configured. There is no agent-level tag
  selection, no custom templates, no "batch up to N values" and no max-payload splitting.
- **`timestamp` and `t` precision.** KEPServerEX takes `t` from the device or driver time of the
  update; opencap uses `source_ts` (the poll time for protocols without a device timestamp,
  ADR-0006). `timestamp` is the publish time, not the time of the newest update.
- **`v` of a bad tag.** The manual does not fix it; KEPServerEX consumers commonly see the last
  value or a default. opencap sends the last known value, or `null` when there is none.
- **Name case and characters.** KEPServerEX names are case-insensitive and restricted (no
  periods in channel and device names); opencap writes names as configured and does not check
  that `id` is unique across devices with dotted names.
- **Data types.** 64-bit integers are exact JSON integers; consumers that parse numbers as
  doubles lose precision above 2^53, as with the SubDevice format. Timestamps and dates tags are
  not represented specially (opencap has no such dtype yet).
