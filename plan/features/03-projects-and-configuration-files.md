# 03 Projects and configuration files

> Source: KEPServerEX V6 server manual (© PTC), pages 144–145, 150–151, 155–158 and 164–174 (project topics and the configuration "How Do I…" pages), summarised in our own words for planning. Status as of 2026-11-18.

## What the manual describes
A KEPServerEX **project** holds the channels, devices, tag groups and tags. Many projects can be
saved, and the server loads the most recently used one at start. Global options live outside the
project, in a `settings.ini` that can be copied between machines (manual p. 144–145, 157). A
project is saved as binary `.opf`, encrypted `.sopf` or plain `.json`. Encryption is on by default
and needs a 14–512 character password, which is asked for again when the file is opened. The
server also keeps automatic backup copies in its data folder (manual p. 155–158). Runtime projects
apply as they are saved. Offline projects are saved and then loaded into the runtime (manual
p. 155–156). The "How Do I…" pages cover configuration practice (manual p. 164–174). Names may not
contain periods, double quotes, a leading underscore, or leading or trailing spaces. One channel
per device gives the best parallelism, within the connection limits of each device. The server
flushes its DNS cache often, so devices that change address after a power cycle are found again.
Clients can address device locations directly (dynamic tags, with `@type,rate` overrides). Serial
devices can sit behind terminal servers ("Ethernet Encapsulation"). A channel setting decides
whether NaN, infinity and denormal floats are passed through or replaced with zero.

## opencap today
- **Project = config directory** (`--config DIR`, default `./config`, `/etc/opencap` under
  systemd): `devices.json` (channels, devices, tags; generated by `opencap import-kep`, hand-editable),
  `devices_map.yaml` (publish settings per device), `overrides.yaml` (hand fixes that survive a
  re-import) and `poller.yaml` (node settings). Layering rules are D-012. Each file has a JSON
  Schema in `schema/`, generated from the Pydantic models and drift-tested (ADR-0003, #71), and
  the Rust engine reads the same files (RFC 0001 §2.8).
- **Import:** `opencap import-kep project.json` (CLI) and `POST /api/v1/project/import` (dry run
  by default; UI import page with a diff) read a KEPServerEX **JSON** project (D-010, D-042). The
  binary `.opf` is not read (FR-9).
- **Saving:** the configuration API (#63) validates every change (model, staged loader run, driver
  `plan()`), then writes atomically with a one-generation `<file>.bak`, keeps comments in the YAML
  files, logs the change to the audit log, and exposes revisions as `ETag`/`If-Match`. A write
  applies on `POST /api/v1/reload` or `?apply=true` (D-039–D-043). `GET /api/v1/project` exports
  the whole config, and importing an export restores it.
- **Project file v2** (`project.json` + `node.yaml`, `config/.revisions/` history,
  `opencap config migrate`, three-way re-import): ADR-0013, proposed. Implementation is #37.
- **Names:** the API refuses `/` in channel and device names, empty names, and the device names
  `tags`, `values`, `plan`, `identity`, `status` and `read-once` (`src/opencap/config/store.py`).
  The models do not check names. Tag group paths are joined with `.` into the tag name
  (`Group.Sub.TAG`, README), although FR-2 says names may not contain `.`.
- **Serial behind TCP gateways:** `params.transport: tcp | rfc2217 | serial | unmapped` and
  `overrides.yaml` `serial_ports` (D-033, D-037, #62). The importer maps COM ports only.
- **Non-normalized floats:** `params.nonnormal_float: zero | unmodified` (default `zero`, imported
  from the channel setting) in `modbus_tcp`, which `modbus_rtu` reuses, and in the Rust Modbus TCP
  decoder. The MQTT payload treats a NaN or infinite value as a bad tag.
- **Dynamic tags:** not built. FR-2 plans them for M5, off by default.

## Features

### PRJ-01 A project is a config directory, loaded at start (manual p. 144, 157)
- **What:** The project defines channels, devices, groups and tags. Several can exist, and the
  server runs the last one used.
- **Decision:** Adapt: a project is a config directory chosen with `--config` (or the service
  unit). There is no "most recently used" list, because the service always says which directory it
  runs.
- **Status:** Done
- **Requirements:**
  - Every command (`run`, `check`, `read`, `identity`, `import-kep`) takes `--config DIR`.
  - Both engines read the same files with the same layering (D-012, RFC 0001 §2.8).
- **Acceptance:** `tests/unit/test_loader.py` and `test_rust_engine_cli.py` (identical `check -v`
  on both engines).

### PRJ-02 Project file v2: one project document plus node settings (manual p. 144, 155)
- **What:** One project file holds the whole configuration.
- **Decision:** Adapt: `project.json` (schema version 2) holds channels, devices, tags, publish
  settings and agents, and `node.yaml` holds per-node settings (ADR-0013). v1 layouts keep loading.
- **Status:** Planned (#37)
- **Requirements:**
  - A `ProjectStore` protocol sits under the config API, with v1 and v2 implementations (ADR-0013
    "Status after #63").
  - `opencap config migrate` writes v2 from v1, and the result loads into the same registry
    (identical `opencap check -v` output).
  - On a v2 project, the v1-only routes (`/map…`, `/overrides…`) answer 409 with a pointer to
    `/channels…`.
  - The JSON Schema for v2 is generated into `schema/` and has conformance fixtures for both
    engines (ADR-0003).
- **Acceptance:** Migration fixtures (v1 in, v2 out) in `tests/conformance/config/`. The config
  API test suite runs against both stores. The Rust engine loads v2 (#39 follow-up).

### PRJ-03 Node settings kept apart from the project (manual p. 144)
- **What:** Global options sit in their own file, which can be copied to another machine.
- **Decision:** Adapt: node settings (instance name, bind addresses, paths, names of secret env
  vars) are in `poller.yaml`, and in `node.yaml` with v2. A redundant pair shares the project, not
  the node file (ADR-0012/0013).
- **Status:** Done
- **Requirements:** `poller.yaml` is optional (missing means defaults). Unknown keys are errors.
  Secrets appear only as env var names.
- **Acceptance:** `tests/unit/test_models.py` and `test_loader.py`. Config fixtures in
  `tests/conformance/config/`.

### PRJ-04 Start a new, empty project (manual p. 144–145)
- **What:** File › New opens an empty project to configure and save.
- **Decision:** Adapt: `opencap init` creates a config directory with an empty project and
  annotated templates. The engine then starts on an empty project, so channels can be added from
  the UI. Today, `run` stops when `devices.json` is missing.
- **Status:** Not started
- **Requirements:**
  - `opencap init [--config DIR]` writes `devices.json` (`{"version": 1, "channels": []}`, or a v2
    `project.json` once #37 lands) and the `poller.yaml`, `devices_map.yaml` and `overrides.yaml`
    templates. It refuses to overwrite an existing file unless `--force` is given.
  - `opencap run` on an empty project starts the API and UI, reports "no channels" in `/health`,
    and polls nothing.
  - Both engines accept the empty project.
- **Acceptance:** CLI test (init, then check, then run, and `/health` answers). A config fixture of
  an empty project for both engines.

### PRJ-05 Validate every change before it is saved (manual p. 150, 155)
- **What:** The server refuses duplicate tag names. The driver refuses a bad address, a data type
  the address cannot have, and an access level it cannot give.
- **Decision:** Adapt: each change is checked by its model, by the real loader in a staging
  directory, and by the affected devices' driver `plan()`. A 422 lists each error with its field
  (D-039). Access is always read-only, so there is nothing to check there (FR-2).
- **Status:** Done
- **Requirements:**
  - Duplicate tag names or device ids, an unknown dtype, and an address the driver cannot plan
    are refused before anything is written.
  - Tags that the change did not touch and that do not plan are warnings, not errors.
  - `opencap check` and `GET /api/v1/project/validate` report the same problems as text and JSON.
- **Acceptance:** `tests/unit/test_config_api.py` and `test_config_store.py`. The UI smoke test
  shows field errors.

### PRJ-06 Save and apply; runtime and offline editing (manual p. 155–156)
- **What:** Edits to the runtime project take effect when it is saved. Offline projects are saved
  and then loaded into the runtime.
- **Decision:** Adapt: an API write changes the files. `POST /api/v1/reload` (or `?apply=true`)
  applies them and restarts only the channels that changed. "Offline" means a config directory
  that is not running: it can be validated with `opencap check --config DIR` and compared with a
  dry-run import.
- **Status:** Done
- **Requirements:**
  - Writes are atomic: temp file, fsync, rename. A multi-file change is all or nothing (D-041).
  - `GET /api/v1/project/pending` says which channels a reload would restart and which settings
    need a process restart.
  - An invalid config on reload keeps the running one (`reload_failed`).
- **Acceptance:** `tests/unit/test_config_store.py` (with fault injection on the second rename),
  `tests/integration/test_runtime_reload.py`, and the Rust API/reload tests.

### PRJ-07 Import a KEPServerEX JSON project (manual p. 155)
- **What:** KEPServerEX can save a project as `.json`.
- **Decision:** Adapt: the JSON project is opencap's migration input. It is converted into
  opencap's files, keeping hand-owned files and fixes (D-010, D-012, D-042). Re-import as a
  three-way merge comes with v2 (ADR-0013, board backlog).
- **Status:** Done
- **Requirements:**
  - `opencap import-kep` writes `devices.json`, appends stubs to `devices_map.yaml`, writes the
    `overrides.yaml` template if it is missing, and writes `reports/import_summary.json` and
    `reports/same_address.csv`.
  - The API import is a dry run by default and shows a diff. Applying it needs `If-Match`.
  - The importer reads a UTF-8 file with a BOM and never copies credentials.
- **Acceptance:** `tests/unit/test_kep_import.py`, `test_kep_import_df1.py`, and the API import
  tests. `real_project` tests run against a private export (skipped in CI).

### PRJ-08 Binary and encrypted project files `.opf` / `.sopf` (manual p. 155–157)
- **What:** Proprietary binary and encrypted project formats.
- **Decision:** Out of scope: undocumented formats. The site saves the project as JSON in
  KEPServerEX once, and imports that (FR-9).
- **Status:** Out of scope

### PRJ-09 Keep projects confidential without encrypting them (manual p. 156–158)
- **What:** The manual recommends encrypted project files, because a project reveals the plant.
- **Decision:** Adapt: opencap project files stay plain, diffable text. Confidentiality comes from
  keeping secrets out of them, and from file permissions on the config directory.
- **Status:** Done
- **Requirements:**
  - No credential is stored in any config file. Files hold env var names only, and the importer
    writes `OPENCAP_OPCUA_<CHANNEL>_*` names instead of copying credentials (D-010).
  - Files written by the API keep their permissions (D-041). Secrets live in the service's env
    file, which the service account cannot replace (`docs/deployment.md`).
  - README and SECURITY.md tell users to treat a KEPServerEX `project.json` as secret.
- **Acceptance:** `tests/unit/test_kep_import.py` (no credential in the output) and
  `test_no_private_data.py`.

### PRJ-10 Encrypted project export (manual p. 156–158)
- **What:** Password-protected project files for transport or archiving.
- **Decision:** Defer to the security RFC (#21, M5): an optional encrypted form of the export
  (`GET /api/v1/project?download=true`) for moving projects between sites. Files on the node stay
  plain.
- **Status:** Not started
- **Requirements:** To be set by #21: algorithm and key handling (passphrase or recipient key),
  restore through `POST /api/v1/project/import`, and no plain-text copy written to disk on the way.
- **Acceptance:** Round-trip test (export encrypted, then import) and a wrong-key test.

### PRJ-11 Automatic backup copies (manual p. 157)
- **What:** The server saves backup copies of the project in its data folder.
- **Decision:** Adapt: each API write keeps the previous version as `<file>.bak`, and the whole
  config can be downloaded and restored.
- **Status:** Done
- **Requirements:**
  - Every changed file has a one-generation `.bak` (a hard link to the old inode).
  - `GET /api/v1/project?download=true` returns every file. Importing that export restores the
    files byte-for-byte, even over files that no longer parse (D-042).
- **Acceptance:** `tests/unit/test_config_store.py` and the export/import tests in
  `test_config_api.py`.

### PRJ-12 Revision history and rollback (manual p. 157)
- **What:** Older project versions can be recovered.
- **Decision:** Adapt: keep the last N revisions in `config/.revisions/`, list them, and roll back
  to one (FR-9 "config revisions with rollback", ADR-0013).
- **Status:** Planned (#37)
- **Requirements:**
  - Every accepted write stores the new revision (files + audit reference). `config.keep_revisions`
    defaults to 50.
  - `GET /api/v1/project/revisions` lists them. `POST /api/v1/project/revisions/{rev}/restore`
    (admin, `If-Match`, audited) restores one as a new revision. Nothing is applied until reload.
- **Acceptance:** API tests (restore, 412 on a stale `If-Match`, audit entry) on both stores.

### PRJ-13 Naming rules for channels, devices, groups and tags (manual p. 167–168)
- **What:** Names may not contain `.` or `"`, may not start with `_`, and may not start or end
  with a space. `_` inside a name and spaces inside a name are fine.
- **Decision:** Adapt: adopt the KEPServerEX rules, so tag paths stay unambiguous and `_` stays
  reserved for system tags (plan 07). Add opencap's own rules (`/` in channel and device names, and
  the reserved device names). Enforce them in the models of both engines, not only in the API.
- **Status:** Not started
- **Requirements:**
  - Channel, device, tag-group and tag names are checked. Each dot-separated segment of a v1 tag
    name counts as a group or tag name. Names must be non-empty, without `.` or `"`, without a
    leading `_` and without leading or trailing whitespace. Channel and device names must also
    not contain `/`, and must not be a reserved device name.
  - In v1 a violation is a `opencap check` and loader **warning**, so existing installations keep
    starting. In v2 (#37) and in new API writes it is an **error** with the offending character
    named.
  - The importer reports KEPServerEX names that break a rule.
  - The messages are identical in both engines.
- **Acceptance:** Valid and invalid fixtures in `tests/conformance/config/`, passing in Python and
  Rust (#39). API 422 tests.

### PRJ-14 The channel is the unit of parallel execution (manual p. 166–167)
- **What:** Each channel is its own execution path. Devices on one channel take turns, so
  spreading devices over channels raises throughput, up to the connections each device allows.
- **Decision:** Adopt (D-015): one worker per channel and one request on the wire per channel.
  `opencap check` estimates cycle time and load per channel.
- **Status:** Done
- **Requirements:**
  - Devices of one channel never have two requests in flight together, and channels run
    concurrently.
  - `opencap check` prints each device's blocks, requests and estimated cycle, a per-channel
    total, and `OVERLOAD` when the estimated load is above 100 %.
  - A serial line is shared by every device on it, whatever their channel (D-033).
- **Acceptance:** `tests/unit/test_channel_worker.py`, `test_scheduler.py`, the Rust worker
  one-request test (flake under investigation, #78), and `test_rust_engine_cli.py`.

### PRJ-15 Optimisation hints (manual p. 166–168)
- **What:** Advice to put each device on its own channel. A device's own connection limit sets the
  ceiling, and aliases keep client references working after the move.
- **Decision:** Adapt: `opencap check` turns its estimate into advice. Moving a device to another
  channel changes its id (`<channel>/<device>`), so the UI move keeps its map entry and override
  (D-039). The alias map that keeps north item names stable is plan 06.
- **Status:** Not started
- **Requirements:**
  - For an overloaded channel with more than one device, `check` names the devices whose move to
    their own channel would bring the estimate under 100 %.
  - `check` warns when several channels poll the same `host:port`, showing the connection count
    against a per-driver known limit where one exists (e.g. Micro800, D-025).
  - `GET /api/v1/project/validate` returns the hints as structured data. The UI check page shows
    them.
- **Acceptance:** `check` output vectors for a fixture project in both engines (CLI parity test).

### PRJ-16 Find devices again after their address changes (manual p. 168)
- **What:** A device that gets a new IP address after a power cycle is reconnected once the name
  resolves again. The server flushes its DNS cache every 30 s for this.
- **Decision:** Adapt: opencap never caches name resolution. Every connect attempt resolves
  `host` again through the OS resolver. Today, Modbus TCP passes the host name on each connect in
  both engines, but nothing tests it and the other drivers are unchecked.
- **Status:** Not started
- **Requirements:**
  - Every network driver resolves `host` on each (re)connect, and keeps no resolved address across
    connects.
  - `device.connected` logs the resolved address, so an address change is visible.
  - The commissioning docs say how to shorten OS-level caching (systemd-resolved, Windows DNS
    client) when devices use DHCP names.
- **Acceptance:** A simulator test per driver family, with a test resolver hook or a hosts-file
  override: the name moves to a second simulator and the next reconnect reaches it. Both engines.

### PRJ-17 Dynamic tag addressing from clients (manual p. 150–151, 170–171)
- **What:** A client item `Channel.Device.<address>` creates a temporary tag without
  configuration. An optional `@<type>` and/or `,<rate ms>` suffix overrides the default type and
  rate, other clients cannot browse these tags, and the device-level `_Error` item reports device
  health.
- **Decision:** Defer to M5 (FR-2): off by default, because it lets any client create load on a
  PLC. When it is built, it follows the KEPServerEX syntax. Plan 06 owns the tag model, and plan 07
  owns `_Error`.
- **Status:** Not started
- **Requirements:**
  - The per-device setting `dynamic_tags: false` (default) and a cap `dynamic_tags_max` (default
    100) apply.
  - `<address>[@<dtype>][,<rate_ms>]` and `<address>@<rate_ms>` are parsed. The rate is floored by
    `min_scan_ms`, and the address is validated by the driver's `plan()` before anything goes on
    the wire.
  - Dynamic tags are never written to the project, never browsable, and are dropped when no
    client uses them for 60 s.
- **Acceptance:** OPC UA L1 test (#29) with a simulator. Parser vectors in both engines.

### PRJ-18 Serial devices behind terminal servers (manual p. 171–172)
- **What:** "Ethernet Encapsulation" reaches serial devices through terminal servers that turn
  TCP/IP into serial. The channel's serial settings are then unused, and each device gets an IP
  address, a port and a protocol.
- **Decision:** Adapt: `params.transport: tcp` (raw TCP to a serial-over-TCP gateway) or `rfc2217`
  (COM-port control). Devices on one line share one connection (D-033). UDP encapsulation and
  unsolicited (listening) drivers are not offered, because opencap only polls.
- **Status:** Done
- **Requirements:**
  - `ab_df1` and `modbus_rtu` support `transport: tcp` (and `rfc2217` for `ab_df1`), with host and
    port of the gateway.
  - `overrides.yaml` `serial_ports` maps a KEPServerEX COM port to a gateway once for every device
    on it.
- **Acceptance:** `tests/integration/test_serial_acceptance.py`, `test_ab_df1_sim.py` and
  `test_modbus_rtu_sim.py`. `tests/unit/test_serial_transport.py`.

### PRJ-19 Import KEPServerEX Ethernet Encapsulation settings (manual p. 171–172)
- **What:** In the exported project, a channel whose connection type is Ethernet Encapsulation
  carries the terminal server's IP address, port and protocol on each device.
- **Decision:** Adapt: the importer maps those settings straight to `transport: tcp` with host and
  port, instead of importing the device as `unmapped` and waiting for a `serial_ports` entry.
- **Status:** Not started
- **Requirements:**
  - For serial drivers that the importer maps (`ab_df1` today, `modbus_rtu` once it has a mapper),
    an encapsulated channel gives `transport: tcp` with the device's encapsulation IP and port.
  - Encapsulation over UDP is imported **disabled**, with a problem line in the summary.
  - The key names are confirmed against a real export (owner), and the summary lists the devices
    mapped this way.
- **Acceptance:** Importer unit tests with a synthetic export fragment (192.0.2.x addresses). A
  `real_project` test when a site has such a channel.

### PRJ-20 Non-normalized floats in the Modbus drivers (manual p. 172–174)
- **What:** A channel setting decides whether NaN, ±infinity and denormal IEEE-754 values reach
  clients unchanged or as zero.
- **Decision:** Adopt: `params.nonnormal_float: zero | unmodified`, default `zero` (the KEPServerEX
  default), imported from the channel setting. In `unmodified` mode, NaN or ±infinity cannot go
  into the JSON payload, so the tag is reported in `BadTags` there. OPC UA will carry the value as
  is.
- **Status:** Done
- **Requirements:** 32- and 64-bit values with an all-ones exponent, or a zero exponent with a
  non-zero mantissa, become `0.0` in `zero` mode. They are decoded unchanged in `unmodified` mode.
  This holds in `modbus_tcp`/`modbus_rtu` (Python) and in Rust `modbus_tcp`.
- **Acceptance:** `tests/unit/test_modbus_decode.py`, the Rust `modbus_tcp/decode.rs` unit tests,
  and the importer test of the channel key.

### PRJ-21 Non-normalized floats in every driver (manual p. 172–174)
- **What:** The setting applies to every driver that reads IEEE-754 values.
- **Decision:** Adopt: one shared helper and one set of vectors, used by every driver that decodes
  floats (AB Logix/PCCC, S7, MELSEC, DF1, OPC UA client, and the Rust ports), so `nonnormal_float`
  means the same everywhere.
- **Status:** Not started
- **Requirements:**
  - `nonnormal_float` is accepted by every driver that decodes float32/float64, with the same
    default and the same importer mapping.
  - Vectors cover both widths: quiet and signalling NaN of both signs, the indeterminate value,
    ±infinity, the smallest and largest denormals, and the smallest normal. Each vector gives the
    expected result in both modes.
- **Acceptance:** `tests/conformance/decode/nonnormal.json` passes in both engines. Each driver's
  simulator suite includes one NaN case.

### PRJ-22 Choosing network cables (manual p. 168)
- **What:** Advice on patch versus crossover cables.
- **Decision:** Out of scope: hardware advice, not software behaviour. Modern ports detect the cable
  type automatically.
- **Status:** Out of scope

## Open questions
- **Naming rules (PRJ-13):** should v1 configs get warnings only, as proposed, or errors after one
  release? Does the reference project contain any name that breaks the rules (for example a
  leading `_`)?
- **Empty project (PRJ-04):** should `opencap run` on a missing `devices.json` start empty (like
  KEPServerEX's default project), or keep refusing and point at `opencap init`?
- **Encrypted export (PRJ-10):** is there a real need to move projects between sites encrypted, or
  are file permissions and the transport channel enough?
- **Encapsulation keys (PRJ-19):** the owner's export has no encapsulated channel today (the DF1
  sites use virtual COM ports). Is the importer mapping worth doing before a site needs it?
- **Milestones:** PRJ-13 is placed in M2 (config contract for both engines). PRJ-04, 15, 16, 19 and
  21 have no milestone yet.
