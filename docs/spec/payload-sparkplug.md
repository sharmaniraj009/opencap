# Sparkplug B payload (edge node) — v1

Status: **v1** (#51): the codec (§1–§7) and the edge node that publishes it (§8).
Implemented by `engine/north/sparkplug` (Rust); the Python engine loads and validates the config and warns. Conformance vectors: `tests/conformance/sparkplug/`,
generated by an independent Python reference (`tests/helpers/sparkplug_ref.py`) on Google's protobuf
runtime and replayed byte for byte by `engine/north/sparkplug/tests/vectors.rs`
([ADR-0014](../adr/0014-conformance-by-simulators-and-vectors.md)).

Normative source: the Eclipse Sparkplug 3.0.0 specification (chapters 4–6). The protobuf schema is
`proto/third_party/sparkplug_b.proto`, Eclipse Tahu v1.0.19, vendored unmodified (EPL-2.0). This page
says how opencap fills it, and pins what the specification leaves open. Decisions: D-087.

## 1. Topics

| Message | Topic | QoS | Retain |
|---|---|---|---|
| NBIRTH, NDATA | `spBv1.0/<group_id>/NBIRTH\|NDATA/<edge_node_id>` | 0 | no |
| NDEATH (the MQTT Will) | `spBv1.0/<group_id>/NDEATH/<edge_node_id>` | 1 | no |
| DBIRTH, DDATA, DDEATH | `spBv1.0/<group_id>/DBIRTH\|DDATA\|DDEATH/<edge_node_id>/<device_id>` | 0 | no |
| NCMD, DCMD (from hosts) | `spBv1.0/<group_id>/NCMD/<edge_node_id>`, `.../DCMD/<edge_node_id>/<device_id>` | — | — |
| STATE (from the primary host) | `spBv1.0/STATE/<host_id>` | — | yes |

An id (group, edge node, device, host) is a non-empty UTF-8 string without `+`, `/`, `#` (spec
4.1.1) and without NUL (not allowed in MQTT topics). An id that breaks this is a config error.

## 2. Edge node and devices

- One Sparkplug **edge node** per opencap instance: `group_id` and `edge_node_id` from config (#51 part 2).
- One Sparkplug **device** per opencap device. Its `device_id` comes from config; the default mapping
  is part 2's to define.
- The **metric name** of a tag is its path below the device, with `/` as the folder separator. A tag
  name's dots are its group path, as in KEPServerEX, so `LTI002.Pv` becomes `LTI002/Pv`. Ignition shows
  each `/` level as a folder.

## 3. Values

### 3.1 Datatypes

| opencap dtype | Sparkplug datatype | Value field | Array datatype (`bytes_value`, packed little-endian) |
|---|---|---|---|
| `bool` | Boolean (11) | `boolean_value` | BooleanArray (32): 4-byte LE count, then bits, first value in the MSB, padding bits 0 |
| `int16` | Int16 (2) | `int_value` = value mod 2^16 | Int16Array (23) |
| `uint16` | UInt16 (6) | `int_value` | UInt16Array (27) |
| `int32` | Int32 (3) | `int_value` = value mod 2^32 | Int32Array (24) |
| `uint32` | UInt32 (7) | `int_value` | UInt32Array (28) |
| `int64` | Int64 (4) | `long_value` = value mod 2^64 | Int64Array (25) |
| `uint64` | UInt64 (8) | `long_value` | UInt64Array (29) |
| `float32` | Float (9) | `float_value` | FloatArray (30) |
| `float64` | Double (10) | `double_value` | DoubleArray (31) |
| `string` | String (12) | `string_value` | StringArray (33): each UTF-8 string followed by NUL; an element containing NUL is an error |
| any scaled tag | Double (10) | `double_value` | DoubleArray (31) |

- **Scaled tags are Double.** A scaled value is always a float, as in the Python engine. A `bool` or
  `string` tag cannot be scaled.
- **Negative Int8/Int16/Int32.** The spec stores these in `uint32` without saying how a negative value
  is written, and the two Eclipse Tahu libraries differ:
  - Tahu Java sign-extends to 32 bits.
  - Tahu Python writes the value plus 2^width.

  opencap writes **value mod 2^width**, the Tahu Python form; −2 as Int16 is 65534. Tahu Java's
  decoder casts (`(short) getIntValue()`), so it reads the same number. The Rust decoder accepts
  both forms.
- **UInt32.** opencap writes UInt32 into `int_value`, the spec's field type. Tahu Java writes
  `long_value`, and its decoder accepts either field; so does ours.
- **Range and type errors.** A value out of range for its datatype, or of the wrong type, is an error
  from the codec. Examples: 40000 as Int16, an int for a Boolean, a float for an Int16. The edge node
  publishes such a tag as null with quality `bad_decode`.

### 3.2 Quality ([ADR-0006](../adr/0006-quality-and-timestamps.md))

Every birth metric carries a `Quality` property: an Int32 holding the OPC DA quality code that Ignition reads.

| opencap | `Quality` | Value |
|---|---|---|
| `good` | 192 (0xC0) | the value |
| `bad_comm` | 24 (0x18) | the last value |
| `stale` | 68 (0x44) | the last value; `is_null` if never read |
| `bad_config` | 4 (0x04) | `is_null: true` (any last value withheld) |
| `bad_decode` | 0 (0x00) | `is_null: true` |

A tag with no value is always `is_null: true`, whatever its quality. When #30 brings the shared
quality table, `engine/north/sparkplug/src/quality.rs` becomes a re-export of it.

### 3.3 Properties

Properties go in a `PropertySet` in this order. Only the ones that apply are present.

1. `Quality` (Int32): always in births. In DDATA, present when the edge node says so (§8: when the quality changed).
2. `engUnit` (String): the tag's `scale.units`.
3. `engLow`, `engHigh` (Double): the tag's `scale.eng_lo` and `scale.eng_hi`.

The names `engUnit`, `engLow` and `engHigh` are what Ignition's MQTT Engine maps to EngUnit,
EngLow and EngHigh. *Verify* this at L2.

## 4. Metrics

| | name | alias | timestamp | datatype | value or `is_null` | properties |
|---|---|---|---|---|---|---|
| NBIRTH and DBIRTH metric | yes | yes | yes | yes | yes | §3.3 |
| DDATA metric | **no** | yes | yes | **no** | yes | `Quality` when it changed |

These are the spec's rules: tck-id-payloads-alias-birth-requirement, -alias-data-cmd-requirement,
-name-birth-data-requirement, -metric-datatype-req and -metric-datatype-not-req. The metric
timestamp is the value's source timestamp in milliseconds since the epoch (UTC). The payload
timestamp is when the message was built.

**Aliases** are unique across the edge node and all its devices (spec 6.4.6). They are handed out
from 1 in birth order:

1. `bdSeq`
2. `Node Control/Rebirth`
3. any other node metrics
4. each device's tags, in config order

The same configuration therefore always gets the same aliases. A configuration change that changes
them is published with a new birth sequence.

## 5. Messages

### 5.1 Sequence numbers

- **`seq`.** NBIRTH carries 0. Every later NDATA, DBIRTH, DDATA and DDEATH of the session carries
  the next value, and 255 wraps to 0. A new NBIRTH (reconnect or rebirth) starts over at 0. NDEATH
  carries no `seq`.
- **`bdSeq`.** 0 on the first MQTT CONNECT, one more on every later CONNECT, and 255 wraps to 0. The
  same value goes into that CONNECT's Will (NDEATH) and into every NBIRTH of the session, including
  one sent after a rebirth.

### 5.2 Payloads

- **NBIRTH:** `seq` 0, metrics `bdSeq` (Int64), `Node Control/Rebirth` (Boolean false), then other node
  metrics (part 2: version, `_System` metrics).
- **NDEATH:** payload timestamp and the one metric `bdSeq` (Int64, no alias). It is built at CONNECT
  time and registered as the Will.
- **DBIRTH:** every enabled tag of the device as a birth metric, with its current value and quality.
- **DDATA:** the changed tags as data metrics.
- **DDEATH:** no metrics.

## 6. Commands (read-only, [ADR-0008](../adr/0008-read-only-by-default.md))

The only command opencap executes is **`Node Control/Rebirth` = `true` in an NCMD**. The host may
address it by name or by its NBIRTH alias. It triggers a new NBIRTH (same `bdSeq`) and every DBIRTH.

Every other metric is rejected and logged, and nothing is written:
- any other NCMD metric, such as `Node Control/Reboot` or a write by alias;
- `Node Control/Rebirth` with a value other than `true`;
- every metric of a DCMD, including one named `Node Control/Rebirth`.

A command whose payload is not Sparkplug B protobuf is rejected as a whole.

## 7. Primary host STATE

The host publishes `{"online": <bool>, "timestamp": <ms>}`. Both keys are required, and other keys
are ignored. An older timestamp never overrides a newer one, because STATE messages can cross
across reconnects.

**Not supported:** the Sparkplug 2.x form, plain-text `ONLINE`/`OFFLINE` on `STATE/<host_id>`
outside the namespace, as sent by older Ignition MQTT Engine versions. Use a host that speaks
Sparkplug 3.0.

## 8. Edge node

### 8.1 Configuration (`poller.yaml`)

```yaml
sparkplug:
  enabled: true
  group_id: Plant A                # default "opencap"
  edge_node_id: opencap-1          # default: `instance`
  primary_host_id: scada           # optional: births only while this host's STATE says online
  client_id: opencap-1-sparkplug   # default: "<mqtt.client_id or instance>-sparkplug"
  devices:                         # opencap device id -> Sparkplug device id
    "Plant A/PLC1": Line1-PLC1     # default "<channel>.<device>"
  outbox: data/sparkplug-outbox.sqlite
  outbox_max_bytes: 67108864
```

- The node connects to the broker of `mqtt` (host, port, TLS, credentials), on **its own**
  connection with its own client id and Will. It runs beside the SubDevice JSON publisher, or
  instead of it when no `mqtt` topics are consumed.
- The rules both engines check at load:
  - ids follow §1;
  - two devices may not map to one Sparkplug device id;
  - while the node is enabled, every enabled device's id (mapped or default) must be valid and
    unique, or the config is refused with a hint to map it in `devices`;
  - an unknown device in `devices` is a warning.
- The `NBIRTH` node metrics are `bdSeq`, `Node Control/Rebirth` and `Node Info/Version`
  (`opencap-<version>`). The `_System` diagnostics follow when the Rust engine has them (#56).

### 8.2 Session

1. CONNECT with a clean session. The Will is NDEATH on the node topic, with QoS 1, not retained,
   and carries the bdSeq of this CONNECT (§5.1).
2. Subscribe, at QoS 1, to:
   - `spBv1.0/<group>/NCMD/<edge>`;
   - `spBv1.0/<group>/DCMD/<edge>/+`;
   - with a primary host, `spBv1.0/STATE/<host>`.
3. Without a primary host, publish the births at once. With one, publish them when a STATE
   message says `online: true` (§7: its timestamp is not older than the last one seen).
4. **Births:** NBIRTH (`seq` 0), then a DBIRTH for every device with its current store values,
   then the held data (§8.4).
5. A STATE message saying `online: false` ends the session: NDEATH, disconnect, and after 2 s a
   new CONNECT with the next bdSeq, which waits again. This is the spec's rule for a primary host
   that lost this server. A lost broker connection reconnects after 1 s, doubling up to 30 s.
6. NCMD `Node Control/Rebirth` repeats step 4 with the same bdSeq.
7. Shutting down (or a config reload that changes the node) publishes NDEATH and disconnects.

### 8.3 Data

- **Report by exception.** The node follows the tag store's change batches. A tag is sent in
  DDATA when its quality changes, or when its value moves by more than the device's
  `publish.deadband` (numbers) or changes at all (other types), compared with what the host was
  last sent. DDATA carries every changed tag of one device; a metric carries the `Quality`
  property when its quality changed. Every DDATA is QoS 0 and not retained (spec).
- **Device state.** Checked every second. A device whose health turns offline or demoted gets
  DDEATH; when it is ok again it gets a DBIRTH with its current values. Its changes in between
  are not sent: the DBIRTH carries the current state.
- A value its datatype cannot carry (out of range, wrong kind) goes out as null with quality
  `bad_decode`.

### 8.4 Holding data while the host is offline ([ADR-0011](../adr/0011-store-and-forward-outbox-per-agent.md))

While there is no session with births (no broker connection, or the primary host offline), each
change batch becomes a DDATA payload. Its metrics have `is_historical: true` and no `seq`, and it
goes into the node's own outbox (`sparkplug.outbox`, SQLite). After the next births, the outbox is
replayed in order, each payload with the next `seq`, then deleted.

The host gets the current state first, in the births, then the history it missed, in
chronological order. This includes values read before the host was first online. The
integration test checks that every value changed while the host was offline arrives, in order.

Limits:
- **Delivery.** DDATA is QoS 0 per the spec, so a row is deleted once handed to the MQTT client.
  A connection lost in that instant can drop the in-flight rows.
- **Size.** The outbox keeps at most `outbox_max_bytes`, dropping the oldest rows first, like
  the SubDevice outbox.
- **Aliases.** A replay after a config change can carry aliases of the old configuration. The
  node is restarted on such a reload, and the replay is still `is_historical`.

### 8.5 Not covered yet

- **The Eclipse Sparkplug TCK.** It runs as a HiveMQ CE extension that an operator drives through
  its web console; there is no headless runner in CI. `tests/integration/test_sparkplug_node.py`
  and the codec unit tests check these tck-ids against amqtt instead:
  - payloads: nbirth-seq, nbirth-bdseq, nbirth-rebirth-req, alias-birth-requirement,
    alias-data-cmd-requirement, metric-datatype-not-req;
  - topics: ndeath-payload, ndeath-seq;
  - message flow: edge-node-birth-publish-phid-wait and its -online and -timestamp checks;
  - operational behaviour: primary-application-state-with-multiple-servers-walk (single
    server), data-publish-dbirth.

  A CI job with HiveMQ CE and the TCK is a follow-up.
- **Multiple brokers.** Walking several MQTT servers is not supported; there is one `mqtt` broker.
- **Templates, DataSets and Sparkplug 2.x STATE** (§7).
